Discord DSA bot UI reference

Source-derived inventory of every current command, modal, select, button, embed family, and lifecycle DM, plus a planning-only proposal for a more explanatory UI. Command responses stay ephemeral. Lifecycle notifications stay ordinary private DMs because Discord does not support ephemeral DMs.

Source: apps/bot/src/commands.ts Source: apps/bot/src/ui.ts Source: apps/bot/src/interactions.ts Source: apps/bot/src/notifier.ts Updated: 28 July 2026
Visual language. The bot uses Discord-native embeds with no author strip, banner, or decorative image. Profile avatars and server icons are used as thumbnails. Blurple means informational, orange means review, yellow means in progress, green means success/actioned, red means failure/rejection, and grey means closed without action.

Planning rules and stable references

This revision is a UI plan, not a runtime change. The proposed style is contextually verbose: explain meaning, consequence, and the next step at decision points without turning every Discord embed into a wall of text.

Surfaces stay private

All command, review, status, error, access, and administration responses remain ephemeral. Lifecycle updates remain ordinary private DMs.

One durable lifecycle DM

The saved DM is edited as the report moves from submitted to received to a final outcome. A final acceptance or denial is a reply to that message.

IDs never get renumbered

Every tree node has a visible immutable ID such as RM-03A. New nodes receive a new suffix so feedback can refer to an exact element.

Privacy boundary remains

Verbose copy must never expose generated identity, email alias, proxy/session details, cookies, verification codes, raw mail, or signing secrets.

Report creation trees

Proposed verbose interaction trees. Every element has a visible immutable ID. The four entry points below open report modals; the other bot commands use inline slash options.

RM /report message

  • RM-01Ephemeral command summaryMessage link, country source, and AI/manual mode. Nothing has been submitted.
    • RM-02Modal: Report MessageWhy are you reporting? plus Briefly explain or Final report text. Helper copy explains the category and 512-character final limit.
      • RM-03AAI drafting branchCountry selection, legal research, and concise drafting. Nothing is sent during preparation.
        • RM-03A-ERRWriter failureNo report was sent. Each recovery action explains its effect.
        • RM-04AOrange reviewNot submitted yet. Target, Evidence, Country, Exact text, Credit effect, and What happens next.
      • RM-03BManual branchThe entered text is the exact proposed submission and moves directly to review.
        • RM-04BOrange reviewSame review composition and controls as the AI path.
      • RM-05BCancelDraft deleted; no report submitted and no credit used.
      • RM-05ASubmitReserve a normal-user credit, create the API report, consume the credit only after creation succeeds, then show status.
        • RM-06Ephemeral Message report statusCurrent phase, receipt-versus-decision explanation, /reports status, and private-DM next step.
        • RM-07Continue at lifecycle treeSee LC-01 onward.

RMC Apps → Report Message

  • RMC-01Selected messagePreview author, channel, timestamp, URL, and identify the snapshot as auto-captured evidence.
    • RMC-02Private capture noticeExplains what was captured and that nothing has been submitted.
    • RMC-03Shared downstream flowOpens Report Message, then follows RM-02 through RM-07.

RP /report profile

  • RP-01Resolve exact Discord accountFetch username, display name, bot flag, and avatar from the supplied user ID.
    • RP-02BLookup unsuccessfulCannot continue; verify the raw user ID and retry. No report or draft was created.
    • RP-02AConfirm this exact accountResolved identity plus a short explanation of why confirmation prevents a wrong-target report.
      • RP-03Modal: Report ProfileReason, Photos/Name/Descriptors, and brief/final text, with examples for each element.
      • RP-04AI or manual preparationSame preparation semantics as RM-03A/RM-03B.
      • RP-05Orange profile reviewIdentity, selected surfaces, snapshot time, country, exact text, credit, and next step.
      • RP-06Submit, status, and lifecycleProfile report embed, then LC-01.

RS /report server

  • RS-01Choose target sourceSupplied server ID/invite, current server, or modal fallback.
    • RS-02Resolution previewBest-effort name, description, counts, and icon; unresolved targets get a clear warning.
    • RS-03Modal: Report ServerTarget if missing, reason, server elements, and brief/final text, with examples for every surface.
    • RS-04AI or manual preparationSame preparation semantics as RM-03A/RM-03B.
    • RS-05Orange server reviewTarget source, identity/snapshot, selected surfaces, country, exact text, credit, and next step.
    • RS-06Submit, status, and lifecycleServer report embed, then LC-01.

LC Shared private lifecycle DM

  • LC-01Report submitted to DiscordSent, but receipt is not confirmed. This message updates automatically; do not create a duplicate.
    • LC-02Report received by DiscordReceipt confirmed. This is not a decision and does not imply action.
      • LC-03AFinal: Discord took actionSame DM turns green and receives an acceptance reply without inventing the action.
      • LC-03BFinal: closed without actionSame DM turns grey and receives the matching final reply.
      • LC-03CFinal: review not approvedSame DM turns red and receives the matching denial reply.
    • LC-04Receipt timeoutReceipt is unconfirmed, not definitely absent. No automatic resubmission; Retry creates a separate lifecycle.
    • LC-05Pre-ID failure proposalStructured red embed: confirmed Discord submission was not established; inspect /reports status before retrying.Planned presentation change

Every command: current UI → planned verbose UI

Complete inventory: 16 slash subcommands plus the Report Message context command. “Planned” describes documentation and proposed presentation only. Amber labels mark proposals that would require an explicit runtime interaction change before implementation.

RM /report message

Current

Inline link/country/AI options → Report Message modal → AI/manual branch → orange review → status embed → private lifecycle DM.

Planned

  • Summarize accepted link, privacy, country source, and drafting mode.
  • Explain brief versus exact final text.
  • Review by Target, Evidence, Country, Exact text, Credit, and Next step.
  • Explain submitted versus received versus decided.

Why

Users should know precisely when a real report begins and what Discord will receive before they spend a credit.

RMC Apps → Report Message

Current

Captures the selected message URL and snapshot, then enters the shared message-report modal and downstream flow.

Planned

  • Preview author, channel, timestamp, and URL.
  • Label the snapshot as automatically captured evidence.
  • Say that only reason/details remain and nothing has been submitted.
  • Cross-reference RMC-03 → RM-02.

Why

The entry surface differs from the slash command even though it shares the later flow.

RP /report profile

Current

Resolves the raw user ID, shows found/failed confirmation, opens Report Profile, then review/status/DM.

Planned

  • Emphasize “this exact account” with resolved identity and snapshot time.
  • Explain Photos, Name, and Descriptors with examples.
  • Give safe next actions after lookup failure.
  • Separate identity, surfaces, country, text, credit, and next step.

Why

Wrong-target reporting is the largest profile-flow comprehension risk.

RS /report server

Current

Resolves a supplied ID/invite or current server, falls back to modal target input, then review/status/DM.

Planned

  • Show which target source won and whether resolution was complete.
  • Explain Name/Icon/Banner/Invite splash/Discovery splash/Welcome screen/Channels/Other.
  • Split review into identity, snapshot, surfaces, text, country, credit, and next step.

Why

Server targeting has multiple sources and the broadest affected-element vocabulary.

RL /reports list

Current

Owner-scoped empty state or one full report embed per page, with Previous/Next and eligible Retry controls.

Planned

  • Show total results, page, newest-first order, privacy scope, and status legend.
  • Explain navigation and retry eligibility.
  • Add predecessor/successor lineage badges and a richer empty state.

Why

A browser needs orientation as well as report detail, especially after retries create linked lifecycles.

RST /reports status

Current

Fetches an owned/admin-visible report and returns the complete type-specific status/history embed plus eligible Retry.

Planned

  • Add Current phase, What this means, What happens next, Notification method, and Final/non-final.
  • Group Target, Content, Processing, and References.
  • Distinguish the internal report ID from Discord’s reference.

Why

A status label alone does not explain whether the user is waiting for receipt or a decision.

RR /reports retry

Current

Checks ownership/access/stage/limit, then immediately creates a fresh lifecycle and returns its status embed.

Planned

  • Add a confirmation card before mutation.
  • Explain new report ID, identity, alias, session, attempt N/3, linked predecessor, and no additional credit.
  • Offer Cancel and Retry as new report.
Behavior change: adds confirmation

Why

Retry is a separate report lifecycle, not an automatic resend of the same submission.

AR /access redeem

Current

Transactionally redeems the supplied key and returns a green embed with the new credit balance.

Planned

  • Show credits added, previous/new balance when available, and remaining submissions.
  • Show only a safe key prefix and state that the key cannot be redeemed again.

Why

The success state should explain both the balance change and the consumed-key consequence without echoing the secret.

AS /access status

Current

Shows credits, suspension, default country, AI usage, and cost in a blurple or red access embed.

Planned

  • Lead with Can submit now: Yes/No and the reason.
  • Explain bypass/default/suspension states and how to obtain credits.
  • Separate reporting credits from AI usage/cost analytics.

Why

Operational eligibility and analytics are different concepts currently presented together.

SC /settings country

Current

Autocompletes Auto or a supported EU country, saves null/ISO code, and returns a green confirmation.

Planned

  • Show previous and new defaults where available.
  • Explain Auto and that the default affects future reports only.
  • Explain that a per-report country overrides it for that report.

Why

A saved default should not be mistaken for a retroactive change to existing reports.

AKC /admin key create

Current

Creates 1–20 hashed keys and displays plaintext once in a green embed.

Planned

  • Summarize count, credits per key, total credits, expiry, creator, and creation time.
  • Prominently warn that plaintext is visible once and must be stored securely.

Why

The one-time secret display is the command’s most important operational consequence.

AKL /admin key list

Current

Shows recent keys with status, credits, expiry, and redeemer in a blurple list embed.

Planned

  • Show totals by status, recency/limit, newest-first order, and a status legend.
  • Use stable row IDs and vertically grouped metadata.
  • Explain inspect/revoke next actions and why plaintext is unavailable.

Why

Administrative scanning improves when scope, status, and follow-up actions are explicit.

AKI /admin key inspect

Current

Fetches an exact key ID and returns a status-colored detail embed.

Planned

  • Add created-by/at, redeemed-at, revoked-by, and reason when available.
  • Translate key status into its practical consequence.
  • Mark unavailable audit fields as future data requirements instead of fabricating them.

Why

An inspection view should answer who, when, current state, and impact.

AKR /admin key revoke

Current

Immediately revokes the key and suspends its redeemer, then returns a green confirmation.

Planned

  • Confirm safe key prefix, status, redeemer, reason, and suspension consequence before mutation.
  • Result shows exactly what changed and whether a user was suspended.
Behavior change: adds confirmation

Why

The current command has a second destructive effect that its result underexplains.

AUI /admin user inspect

Current

Validates a Discord snowflake and returns access state plus suspension reason.

Planned

  • Lead with Can submit now and why.
  • Group Identity, Access, Usage, and Audit.
  • Explain bypass/provenance when available, zero credits, default country, suspension, and available admin actions.

Why

Admins need an actionable eligibility answer, not only stored values.

AUS /admin user suspend

Current

Immediately suspends the user, clears remaining credits, and returns a green confirmation.

Planned

  • Confirm user, current credits, reason, submission block, and credit-clearing effect.
  • Result shows before/after state, actor/time, and that reinstatement returns with zero credits.
Behavior change: adds confirmation

Why

Clearing credits is destructive and should be explicit before and after the operation.

AUR /admin user reinstate

Current

Immediately returns the user to active status with zero credits and shows a green confirmation.

Planned

  • Confirm current state and previous reason before the change.
  • Explain that credits are not restored and the user needs a new key unless bypassed.
  • Offer the next administrative action.
Behavior change: confirmation recommended

Why

Reinstated does not mean immediately able to submit; the zero-credit consequence needs prominence.

Lifecycle DM flow

  1. SubmittedSend one status embed and save its Discord message ID.
  2. ReceivedEdit that same embed; do not create a second status message.
  3. OutcomeEdit the embed to green/grey/red and reply beneath it.
  4. Receipt timeoutEdit red, reply with the two-minute explanation, show retry.
  5. Pre-ID failureSend plain text with failure detail and internal report ID.
  6. ReconciliationWebhook events plus a 15-minute paginated API event feed.
